# Mathematical model and implementation

[Repository](../../README.md) · [Algorithms](../algorithms/README.md) · [Experimental protocol](../experiments/README.md)

This chapter is the technical companion to **Scalable Full-Horizon SFC Deployment over Predictable SAGIN Topologies via Configurable Column Generation Framework**. It explains the original admission-and-deployment ILP, its request-based Dantzig–Wolfe reformulation, and the relationship between mathematical feasibility and executable columns. The [algorithm chapter](../algorithms/README.md) explains how these formulations are used computationally.

The notation follows the manuscript. Equations in this document are numbered sequentially in their order of appearance. The numbering is local to this document and independent of the manuscript. Index scopes appear in the surrounding text when including them in an equation would obscure its structure.

## 1. Notation and indexing

The extended chain has $`|\hat V_r|=|V_r|+2`$ stages, indexed from 0 through $`|V_r|+1`$, and $`|H_r|=|V_r|+1`$ virtual links, indexed from 1 through $`|V_r|+1`$.

### 1.4 Column-generation quantities

| Symbol | Meaning and domain | Implementation correspondence |

| $`C_p^r`$ | Dimensionless normalized resource cost of a column; rejection costs zero | `path_cost` |
| $`C_{\mathrm{node}},C_{\mathrm{link}}`$ | Aggregate normalized computing and communication consumption | Components combined by `compute_usage_physical_cost` |
| $`w_p^r`$ | Column-selection variable: binary in integer master, nonnegative continuous in LP master | `solve_rmp` variable `w[path_id]` |

| $`\pi_{n^t},\eta_{e^t}`$ | Nonnegative dual prices of computing and communication capacity rows | `duals["node"]`, `duals["edge"]` |

Column coefficients are constants once a deployment is constructed; only $`w_p^r`$ is optimized in the master. Resource dual prices have objective units per computing or data unit, so their products with $`\alpha`$ and $`\beta`$ are comparable to the column's objective value.

**Index conversion.** Subtract one from manuscript slots, including both arrival and deadline, when constructing code inputs. A manuscript processing stage $`k`$ has `Path` stage index $`k-1`$, but extended ILP index $`k`$. A manuscript virtual link $`l`$ has code segment index $`l-1`$. Repeated VNF types remain distinct processing stages. The code does not identify placements only by VNF type.

## 2. Full-horizon network representation

The physical network integrates computing and communication resources across ground, air, and space. Layer membership describes the physical infrastructure; deployment uses the resulting capacities and available connections. The formulation does not impose a different conservation law for each layer. The [structured topology generator](../../sagin_generator.py) supplies layer-dependent topology and capacity inputs, while [Network](../../data_model.py) exposes a common directed graph interface to all solvers.

The topology is quasi-static within each slot and may change between slots. The manuscript horizon is $`T=\{1,\ldots,|T|\}`$, and the expanded graph has $`E^T=E_{\mathrm{com}}^T\cup E_{\mathrm{sto}}^T`$. Every physical node has a separate copy in every slot, with its own computing budget. A physical node used in two slots therefore consumes two distinct resource budgets. Likewise, a communication connection available in several slots creates separate directed time edges; capacity in one slot cannot be transferred to another by a capacity constraint.

For communication, the manuscript relates availability, rate, and slot duration by

```math
d(e^t)=\mu(e^t)c(e^t)\tau,\qquad e^t\in E_{\mathrm{com}}^T.
```

Each direction is accounted separately. The implementation represents unavailable connections by absent edges rather than routing variables constrained to zero, and stores $`d(e^t)`$ directly. Multiplying these code capacities by $`\tau`$ again would change the instance. The manuscript's potential-link notation and the code's sparse available-link representation describe the same usable communication graph.

A storage link preserves the physical node and advances time by one slot. It represents keeping the request's data there until the next slot, whether before, between, or after processing stages. It neither performs a VNF nor transmits to another physical node. Storage is unlimited and has zero communication cost in the studied model; it contributes to temporal connectivity but creates no finite capacity row or normalization term. There is no outgoing storage edge in the final slot or incoming storage edge in the first slot. For a single-slot instance, there are no storage edges at all.

This representation permits planning an entire request against future connectivity: a deployment may process now, wait at a node, and transmit when a later connection becomes available. It is an offline full-horizon plan using known inputs, rather than a packet-level scheduler or an online prediction policy. A route can contain multiple communication hops and ordered processing operations within one slot. The assumed slot duration accommodates those operations; the model does not compute their individual propagation or processing delays. Effective directed rates already reflect an externally determined feasible allocation of physical communication resources. Interference scheduling, duplexing allocation, finite-buffer contention, VNF instance provisioning, and live migration are not additional decisions in this ILP.

## 3. Requests and complete deployments

A request specifies the time-expanded source, physical destination with its deadline, ordered processing stages, virtual links, and data amount:

```math
r=\bigl(n_{r,o}^{t_{r,o}},n_{r,d}^{t_{r,d}^{\max}},V_r,H_r,f_r\bigr).
```

The destination superscript denotes the latest permissible delivery time, not a requirement to arrive exactly then. The selected destination copy may be earlier. The same amount $`f_r`$ is processed at every stage and carried by every virtual segment; there are no stage-dependent traffic expansion or compression factors in this formulation.

For example, two processing stages give the logical sequence

```math
v_{r,0}\xrightarrow{h_{r,1}}v_{r,1}
\xrightarrow{h_{r,2}}v_{r,2}\xrightarrow{h_{r,3}}v_{r,3}.
```

Stages 0 and 3 are endpoint dummies and consume no computing resource. If the processing locations are $`a`$ and $`b`$, the three segments connect the source to $`a`$, $`a`$ to $`b`$, and $`b`$ to the selected destination copy. Each segment may contain multiple physical links and storage links. If $`a=b`$ as **time-expanded** nodes, their connecting segment can be empty: processing order is still specified by stage identity. The same physical node in a later slot is a different location and requires temporal traversal.

A complete admitted deployment assigns every actual stage once, connects consecutive stages by ordered unsplit routes, starts at arrival, finishes by the deadline, and fits its resource requirements. Across requests, their combined usages must also fit the shared capacities. Passing through a node capable of processing does not execute a VNF automatically; execution is determined by placement. A node may be revisited by different virtual segments, and different stages may share a processing node if their combined demand fits.

## 4. Original ILP constraints

### 4.1 Admission, endpoints, and unique placement

For each request, the source dummy is fixed at its given arrival copy:

```math
y_{n_{r,o}^{t_{r,o}}}^{v_{r,0}}=x_r. \qquad \text{(1)}
```

The destination dummy selects one destination copy in the inclusive service window:

```math
\sum_{t'=t_{r,o}}^{t_{r,d}^{\max}}y_{n_{r,d}^{t'}}^{v_{r,|V_r|+1}}=x_r. \qquad \text{(2)}
```

Every extended stage, including both dummies, obeys

```math
\sum_{n^t\in N^T}y_{n^t}^{v_{r,k}}=x_r, \qquad v_{r,k}\in\hat V_r. \qquad \text{(3)}
```

Because placements are binary, an admitted request receives exactly one location per stage. A rejected request receives none. Equation (1) together with (3) excludes other source copies; (2) together with (3) excludes other destination nodes and late delivery. No partial chain can collect admission reward. The sum in (3) is over the entire horizon, not one execution per slot.

The direct ILP explicitly sets $`y_{n^t}^{v_{r,k}}=0`$ outside the arrival–deadline window (`time_window` rows). Its `source`, `destination`, and `place_once` rows implement (1)–(3). The pricing MIP uses fixed admission and endpoint/conservation constraints rather than copying these explicit time-window rows. For a connected ordered route in a graph with no backward-time arcs, all intermediate stages lie between its source and destination times. Extraction and validation check the returned stage locations and routes; this connection is important when interpreting the pricing formulation. For valid connected deployments the explicit window rows do not exclude a route admitted by the paper: time never decreases along the concatenated source-to-destination chain. This does not imply that degree/balance constraints prohibit disconnected unused cycles; those remain a separate issue below.

### 4.2 Availability and degree bounds

The binary domains and availability restriction are part of the mathematical model, for every request, extended stage, and applicable time edge:

```math
x_r\in\{0,1\},\qquad y_{n^t}^{v_{r,k}}\in\{0,1\},\qquad z_{e^t}^{h_{r,l}}\in\{0,1\},\qquad z_{e^t}^{h_{r,l}}\le\mu(e^t).
```

Communication variables use $`e_{n^t m^t}^{t}`$; storage variables use $`e_{n^t n^{t+1}}^{t}`$ only for $`t\lt|T|`$. The source and destination stages are included in the placement domain. In code, no variable is created for an unavailable edge. Extending that sparse variable vector by zeros on unavailable directions recovers the availability-constrained formulation; omitting those fixed-zero variables does not relax the model.

For every request, virtual segment, and time-expanded node, incoming and outgoing selections obey

```math
\sum_{m^t\in\Phi_{n^t}}z_{e_{n^t m^t}^{t}}^{h_{r,l}}+\mathbf1\{t\lt|T|\}z_{e_{n^t n^{t+1}}^{t}}^{h_{r,l}}\le1,
```

```math
\sum_{m^t\in\Phi_{n^t}}z_{e_{m^t n^t}^{t}}^{h_{r,l}}+\mathbf1\{t\gt1\}z_{e_{n^{t-1}n^t}^{t-1}}^{h_{r,l}}\le1.\qquad\text{(4)}
```

The two inequalities in (4) form the outgoing/incoming degree system. Here $`\mathbf1\{A\}`$ is 1 when $`A`$ holds and 0 otherwise. A nonexistent boundary-storage term is defined as zero without introducing a variable. In particular, incoming storage departs at $`t-1`$, whereas outgoing storage departs at $`t`$. The neighbor set contains same-slot communication neighbors in either direction; an unavailable direction has a fixed-zero routing variable. Thus a segment cannot both transmit and wait along two outgoing branches at one node copy, or merge two incoming branches there. These are per-segment bounds, not a prohibition on several requests or segments using the same resource.

### 4.3 Flow conservation, processing order, and time

For the same index scope as (4), conservation requires

```math
\begin{aligned} &\sum_{m^t\in\Phi_{n^t}}\left(z_{e_{m^t n^t}^{t}}^{h_{r,l}}-z_{e_{n^t m^t}^{t}}^{h_{r,l}}\right)\\ &\quad+\mathbf1\{t\gt1\}z_{e_{n^{t-1}n^t}^{t-1}}^{h_{r,l}}-\mathbf1\{t\lt|T|\}z_{e_{n^t n^{t+1}}^{t}}^{h_{r,l}}=y_{n^t}^{v_{r,l}}-y_{n^t}^{v_{r,l-1}}.\qquad\text{(5)}\end{aligned}
```

**Equivalence to the implementation's incidence sums.** For a fixed time node, partition its outgoing edges into available same-slot communication edges and its single outgoing storage edge, if present. These disjoint sets exhaust $`\delta^+(n^t)`$; the analogous incoming partition exhausts $`\delta^-(n^t)`$. Substituting the partitions into their sums gives exactly the two left sides in (4), with every directed edge counted once. Incoming minus outgoing then gives (5), with the same destination-minus-source placement RHS. Unavailable communication directions contribute zero. At $`t=1`$ the incoming storage term vanishes; at $`t=|T|`$ the outgoing term vanishes; both vanish for a single-slot horizon. This establishes equality of the constraint rows, not just similar routing intent. Code segment index $`l-1`$ corresponds to the displayed virtual link $`h_{r,l}`$.

At a distinct starting placement, the right side is −1, so one outgoing arc is required. At its distinct ending placement it is +1, so one incoming arc is required. At other nodes it is zero, giving transit balance. With binary variables and the degree bounds, these rows connect each consecutive pair of stages without traffic splitting. If both endpoint stages share a time node, the right side vanishes there and an empty segment is feasible.

Processing order follows from the **combination** of unique placements and the consecutive-stage segments. Temporal order follows from their directed TEG routes: communication preserves time and storage advances it. There is no extra inequality requiring successive VNFs to occupy strictly later slots. At the horizon boundaries, missing storage arcs contribute no terms. With one slot, (5) reduces to ordinary communication-only balance.

An important qualification is that balance and degree rows can also admit disconnected circulations. In particular, zero placements for a rejected request do not alone force every routing variable to zero. Removing such circulations preserves the desired deployment and cannot increase its resource cost. The optional `enforce_simple_routes` constraints in [solve_ilp](../../ILP_solver.py) exclude per-segment cycles using order variables. [reconstruct_ordered_route](../../data_model.py) instead rejects selected arc sets with cycles or unused/disconnected edges during extraction; it does not silently repair them. Consequently, a solver incumbent and an extracted valid deployment are distinct stages of the implementation pipeline.

### 4.4 Computing and communication capacity

At each time-expanded node, computing demand from **all** processing stages and requests is aggregated:

```math
\sum_{r\in R}\sum_{v_{r,k}\in\hat V_r} f_r\delta_{v_{r,k}}y_{n^t}^{v_{r,k}}\le c(n^t), \qquad n^t\in N^T. \qquad \text{(6)}
```

The product $`f_r\delta_{v_{r,k}}`$ is the processing amount required by that stage. Dummy terms vanish. If two stages share a node copy, both terms count; passing through a node without executing a stage consumes no computing resource. The time index belongs to the resource itself, so there is no additional sum over time on the right side.

At each directed communication time edge, every virtual-link use consumes the full data amount:

```math
\sum_{r\in R}\sum_{h_{r,l}\in H_r} f_r z_{e^t}^{h_{r,l}}\le d(e^t), \qquad e^t\in E_{\mathrm{com}}^T. \qquad \text{(7)}
```

If two virtual segments of one request use the same communication edge, the request consumes $`2f_r`$ there. Deduplicating a flattened route before computing usage would therefore be wrong. The reverse direction is a different capacity row. Storage remains part of routing in (4)–(5), but is excluded from (7) because it has no finite capacity in this model.

These are the two constraint families that couple requests. [solve_ilp](../../ILP_solver.py) constructs their aggregate rows. [validate_path](../../validation.py) checks stage identity, endpoints, segment continuity, temporal semantics, stored usage, and cost; [validate_solution_capacity](../../validation.py) checks summed capacity usage. The former is **not**, by itself, a capacity-feasibility certificate for arbitrary externally supplied columns. Built-in PFE and default pricing enforce single-request capacity during construction, and the master enforces aggregate capacity during selection.

## 5. Admission-first, cost-aware objective

The resource totals count each time-expanded resource once:

```math
\mathcal C=\sum_{n^t\in N^T}c(n^t), \qquad \mathcal D=\sum_{e^t\in E_{\mathrm{com}}^T}d(e^t). \qquad \text{(8)}
```

The two normalized usages are

```math
C_{\mathrm{node}}=\frac{1}{\mathcal C} \sum_{n^t\in N^T}\sum_{r\in R}\sum_{v_{r,k}\in\hat V_r} f_r\delta_{v_{r,k}}y_{n^t}^{v_{r,k}}. \qquad \text{(9)}
```

```math
C_{\mathrm{link}}=\frac{1}{\mathcal D} \sum_{e^t\in E_{\mathrm{com}}^T}\sum_{r\in R}\sum_{h_{r,l}\in H_r} f_r z_{e^t}^{h_{r,l}}. \qquad \text{(10)}
```

The objective is

```math
\max\quad M\sum_{r\in R}x_r -\psi C_{\mathrm{node}}-(1-\psi)C_{\mathrm{link}}. \qquad \text{(11)}
```

Admission is prioritized because limited resources may make serving every request impossible. Normalization makes computing and communication consumption dimensionless and comparable; $`\psi`$ controls their relative influence. The denominators use original total capacities, not the capacities left after a heuristic assignment. Storage is excluded from both communication numerator and denominator, avoiding infinite normalization and matching its zero communication cost.

Summing (6) and (7) over their respective resources gives both normalized usages in the interval from 0 to 1. Their weighted sum is therefore also between 0 and 1. For two feasible integer deployments differing by at least one admitted request, the higher-admission deployment improves (11) by at least $`M-1\gt0`$, even if its resource cost increases by the largest possible amount. Among equal admission counts, maximizing (11) minimizes weighted cost. This admission-priority argument relies on aggregate feasibility, positive finite denominators, and $`M\gt1`$; it does not establish that a heuristic finds the maximizing deployment.

The experiments use $`M=2`$ and $`\psi=0.5`$. [objective.py](../../objective.py) centralizes the bound, denominators, costs, admission value, and rejection value. For a fixed admitted set, total computing demand is independent of stage placement, though placement changes which node constraints bind. Communication cost depends on the total segment traversals. Different horizons change normalization totals, so normalized cost values across horizons require care in interpretation.

The manuscript's cost expressions also use an outer slot sum. There, each inner resource sum refers to copies in that slot. Equations (8)–(10) use full-horizon sets directly and are equivalent under that convention; they do not count every time copy once for every outer slot.

## 6. Request-based Dantzig–Wolfe reformulation

### 6.1 What is separated, and why

The direct ILP jointly chooses admissions, placements, and routes. A longer horizon adds possible execution locations, routing arcs, and resource rows. Binary routing decisions across all requests make the joint problem difficult; the manuscript establishes NP-hardness by a 3-PARTITION reduction. Decomposition does not remove that difficulty or make the pricing MIP polynomial. It replaces explicit request decisions in the master by complete feasible alternatives and generates only selected alternatives.

Endpoint, placement, availability, ordering, and temporal requirements involve one request at a time. Shared computing and communication constraints couple different requests. The local request set additionally retains the original capacities as individual upper bounds:

```math
\sum_{v_{r,k}\in\hat V_r}f_r\delta_{v_{r,k}}y_{n^t}^{v_{r,k}} \le c(n^t),\qquad n^t\in N^T. \qquad \text{(12)}
```

```math
\sum_{h_{r,l}\in H_r}f_r z_{e^t}^{h_{r,l}} \le d(e^t),\qquad e^t\in E_{\mathrm{com}}^T. \qquad \text{(13)}
```

These bounds follow from the shared capacity inequalities because all request usages are nonnegative. They therefore preserve every original feasible integer deployment, while excluding individually impossible alternatives without allocating resources to other requests. Their retention can strengthen a decomposition relaxation compared with relaxing the original binary variables directly; equality of the two LP relaxations is not asserted. If several stages of this request share one node, or several segments reuse one communication edge, their usages still add. A column may conflict with another column and remain individually valid; the master decides whether they can be selected together.

### 6.2 Complete columns and their coefficients

An admitted column records the complete stage placement and every ordered virtual-link route, including waiting. Its coefficient triple $`(a_p^r,\mathbf b^{p,r},\mathbf g^{p,r})`$ is a fixed realization of the original binary variables, with bold vectors collecting its placement and routing indicators. A rejection column has admission zero, no placements or routes, zero usage, and zero value. It is a genuine rejection option, not a positive-penalty artificial variable intended to disappear.

Define its demand-weighted resource coefficients and normalized cost by

```math
\alpha_{n^t}^{r,p} = \sum_{v_{r,k}\in\hat V_r} f_r\delta_{v_{r,k}}b_{n^t}^{p,v_{r,k}} \qquad \text{(14)}
```

```math
\beta_{e^t}^{r,p}=\sum_{h_{r,l}\in H_r} f_r g_{e^t}^{p,h_{r,l}},\qquad e^t\in E_{\mathrm{com}}^T. \qquad \text{(15)}
```

```math
C_p^r=\frac{\psi}{\mathcal C}\sum_{n^t\in N^T}\alpha_{n^t}^{r,p} +\frac{1-\psi}{\mathcal D}\sum_{e^t\in E_{\mathrm{com}}^T}\beta_{e^t}^{r,p}. \qquad \text{(16)}
```

`Path.finalize_usage` stores sums of processing coefficients in `path_node_usage` and traversal counts in `path_edge_usage`. They are **not** the demand-weighted $`\alpha`$ and $`\beta`$; objective and master routines multiply by `flow_demand` exactly once. Storage can appear in route/usage records, but has no communication cost or finite master resource row.

Each request has finitely many binary configurations, so its convex hull is bounded despite unlimited storage capacity. Infinite buffer capacity does not make a binary routing variable unbounded; no extreme rays are needed. The convex representation is

```math
(x_r,\mathbf y_r,\mathbf z_r) =\sum_{p\in\hat P_r}w_p^r(a_p^r,\mathbf b^{p,r},\mathbf g^{p,r}), \qquad \sum_{p\in\hat P_r}w_p^r=1,\quad w_p^r\ge0. \qquad \text{(17)}
```

The bold coefficient vectors simply collect the placement and routing coefficients in the table. With binary weights, (17) selects one deployment or rejection. With nonnegative continuous weights, it describes a convex relaxation of whole deployments, not a physically split execution of the request.

### 6.3 Full master, restricted master, and LP relaxation

The full integer master has the following objective and rows:

```math
\max_{\mathbf w}\quad \sum_{r\in R}\sum_{p\in\hat P_r}(Ma_p^r-C_p^r)w_p^r. \qquad \text{(18)}
```

```math
\sum_{p\in\hat P_r}w_p^r=1,\qquad r\in R. \qquad \text{(19)}
```

```math
\sum_{r\in R}\sum_{p\in\hat P_r}\alpha_{n^t}^{r,p}w_p^r \le c(n^t),\qquad n^t\in N^T. \qquad \text{(20)}
```

```math
\sum_{r\in R}\sum_{p\in\hat P_r}\beta_{e^t}^{r,p}w_p^r \le d(e^t),\qquad e^t\in E_{\mathrm{com}}^T. \qquad \text{(21)}
```

```math
w_p^r\in\{0,1\},\qquad r\in R,\quad p\in\hat P_r. \qquad \text{(22)}
```

The request equality prevents choosing two deployments for one request and permits rejection. Capacity rows combine the coefficients of selected columns; all internal routing and placement feasibility has already been encoded in those columns. This explains why adding a column adds an alternative, not a resource reservation.

With every feasible column available, the integer master has the same optimal value as the original ILP under the paper's nonnegative resource costs. This is an optimal-value equivalence, not a one-to-one correspondence with every raw binary routing vector that contains unused circulations: a selection reconstructs feasible original decisions, and original solutions can be encoded after deleting unused circulations without worsening the objective. Explicit enumeration is impractical, so the integer **restricted** master replaces $`\hat P_r`$ by the generated set $`\hat P'_r`$ in every row. Its feasible region can exclude better original deployments simply because their columns were never generated. The request set $`\mathcal F_r`$ uses the endpoint, placement, availability, routing and temporal requirements in Sections 3–4 together with (12)–(13), and includes the all-zero rejection choice. Resource coupling between different requests appears only in the master rows.

Column generation solves the **LP relaxation** of that restricted master, replacing (22) by nonnegativity. Convexity already implies an upper bound of 1. [solve_rmp](../../restricted_master_problem.py) deliberately omits redundant continuous upper bounds so column marginal values are represented by the row duals used for pricing. It returns duals only after an optimal LP solve. Rejection columns ensure that the initial RMP is feasible even when no admitted column exists.

The final integer solve reinstates binary selection over the generated pool. It does not continue pricing inside a branch-and-bound tree. Consequently, solving that finite integer RMP optimally is generally weaker than solving the original ILP globally, even if the preceding full-master LP has been certified.

## 7. Dual prices and request pricing

### 7.1 Dual of the current restricted LP

For a maximization master with capacity inequalities of the form “usage at most capacity,” resource duals are nonnegative. The request equality multiplier is unrestricted. The restricted LP dual is

```math
\min\quad \sum_{r\in R}\sigma_r +\sum_{n^t\in N^T}c(n^t)\pi_{n^t} +\sum_{e^t\in E_{\mathrm{com}}^T}d(e^t)\eta_{e^t}. \qquad \text{(23)}
```

For every generated column $`p\in\hat P'_r`$ of each request $`r`$, it requires

```math
\sigma_r+\sum_{n^t\in N^T}\pi_{n^t}\alpha_{n^t}^{r,p} +\sum_{e^t\in E_{\mathrm{com}}^T}\eta_{e^t}\beta_{e^t}^{r,p} \ge Ma_p^r-C_p^r. \qquad \text{(24)}
```

```math
\sigma_r\in\mathbb R,\qquad \pi_{n^t}\ge0,\qquad \eta_{e^t}\ge0. \qquad \text{(25)}
```

The rejection column contributes $`\sigma_r\ge0`$ to (24), although the equality multiplier's formal domain remains unrestricted. A high resource dual makes using that resource less attractive in pricing: it reflects competition under the current restricted LP. These are optimization shadow prices, not bandwidth tariffs or additional physical consumption. A binding capacity need not have a strictly positive price, particularly in a degenerate LP.

### 7.2 Reduced cost and its sign

Subtracting the left side of (24) from the column's objective coefficient gives

```math
\zeta_p^r=Ma_p^r-C_p^r-\sigma_r -\sum_{n^t\in N^T}\pi_{n^t}\alpha_{n^t}^{r,p} -\sum_{e^t\in E_{\mathrm{com}}^T}\eta_{e^t}\beta_{e^t}^{r,p}. \qquad \text{(26)}
```

Thus positive reduced cost violates the corresponding full-master dual constraint and identifies an eligible improving column in this **maximization** convention. Zero or negative reduced cost does not qualify. Positive reduced cost is an insertion criterion; it does not promise that the next reoptimized master objective strictly increases, since degeneracy can prevent an immediate objective gain. The rejection column has reduced cost $`-\sigma_r\le0`$ and is already present.

Expanding $`C_p^r`$ in (26) combines physical cost and dual resource charges. To keep the pricing expression readable, define the effective unit charges

```math
\tilde\pi_{n^t}=\pi_{n^t}+\frac{\psi}{\mathcal C}, \qquad \tilde\eta_{e^t}=\eta_{e^t}+\frac{1-\psi}{\mathcal D}. \qquad \text{(27)}
```

These are abbreviations, not new independent dual variables. Pricing maximizes the following expression over $`(x_r,\mathbf y_r,\mathbf z_r)\in\mathcal F_r`$:

```math
\begin{aligned} \max\quad &Mx_r-\sigma_r -\sum_{n^t\in N^T}\tilde\pi_{n^t}   \sum_{v_{r,k}\in\hat V_r}f_r\delta_{v_{r,k}}y_{n^t}^{v_{r,k}}\\ &-\sum_{e^t\in E_{\mathrm{com}}^T}\tilde\eta_{e^t}   \sum_{h_{r,l}\in H_r}f_r z_{e^t}^{h_{r,l}}. \qquad \text{(28)} \end{aligned}
```

The admitted-column search in [solve_sp_detailed](../../sub_problem.py) fixes admission to 1, making the first term the constant $`M-\sigma_r`$. It retains the original single-request capacities by default (`enforce_individual_capacity=True`). Subtracting current LP allocations from those capacities would incorrectly forbid alternatives intended to replace current allocations. Resource competition enters through dual prices here and through shared rows when the master is solved again.

### 7.3 Candidate verification and certification are different

PFE or a time-limited pricing MIP can produce a useful feasible candidate without optimizing (28). [extract_path_from_sp](../../sub_problem.py) reconstructs ordered segments, [compute_reduced_cost_from_usage](../../objective.py) evaluates (26) from actual usage, and `GBSolver.solve` checks cost, validity, and duplication before insertion. Calling this an exact reduced-cost check means evaluating the stated expression, subject to floating-point tolerances; it does **not** mean that the candidate generator solved pricing exactly.

To establish full-master LP optimality mathematically, every request must have no positive-reduced-cost alternative under the **same optimal LP-RMP dual solution**. Optimal pricing values or valid upper bounds can establish that fact. A positive candidate proves existence; failure to find one does not prove absence. The current [certification checker](../../result_schema.py), `evaluate_exact_pricing_certification`, uses a conservative rule requiring all expected strict calls to complete optimally, no positive result, no timeout/failure, and no rejected positive candidate. An admitted-only pricing model that proves infeasibility is mathematically informative, but this checker does not count `INFEASIBLE` as an optimal strict call.

Numerical termination uses $`\varepsilon_{\mathrm{rc}}`$, so it is a tolerance-based certificate rather than an exact zero-threshold proof. If pricing stops without a certificate, the restricted LP value is not a certified upper bound on the original integer optimum: restricting columns lowers a maximization optimum, whereas relaxing integrality raises it, and their combined ordering against the original ILP is not fixed. A validated integer selection remains feasible regardless of that certification status.
